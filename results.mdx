## Test and execution

| Resource | Meaning |
| --- | --- |
| Test | Your instructions and one execution per selected environment; ID starts with `test_` |
| Execution | One environment's browser work and evidence; ID starts with `exec_` |

## Follow status

Replace `TEST_ID` with the ID returned when you created the test. Read it about
every two seconds until its status is terminal.

<CodeGroup>

```bash cURL
curl --fail-with-body "https://api.browserbunny.dev/v1/tests/TEST_ID" \
  -H "Authorization: Bearer $BROWSERBUNNY_API_KEY"
```

```python Python
from browserbunny import BrowserBunny

with BrowserBunny() as client:
    test = client.tests.get("TEST_ID")
    print(test)
```

```javascript JavaScript
const response = await fetch("https://api.browserbunny.dev/v1/tests/TEST_ID", {
  headers: {
    Authorization: `Bearer ${process.env.BROWSERBUNNY_API_KEY}`
  }
});
const test = await response.json();
if (!response.ok) throw new Error(JSON.stringify(test));
console.log(test);
```

</CodeGroup>

### Active statuses

| Status | Meaning |
| --- | --- |
| `queued` | Waiting to start |
| `running` | Executing the test |
| `cancelling` | Finishing cancellation and cleanup |

### Terminal statuses

| Status | Meaning |
| --- | --- |
| `passed` | Requested checks passed |
| `failed` | A requested check failed |
| `inconclusive` | Available evidence could not establish the result |
| `error` | Preparation or execution could not complete |
| `cancelled` | The test was cancelled |

Test status becomes terminal after every execution finishes, including browser cleanup.

### Mixed execution results

The aggregate status uses the first matching status in this order:

1. `error`
2. `failed`
3. `cancelled`
4. `inconclusive`
5. `passed`

Inspect individual executions to see each environment's result.

## Read the test response

### Completion counts

Read the fields inside `execution_counts`:

| Field | Meaning |
| --- | --- |
| `total` | Number of executions |
| `finished` | Number finished, including failures and cancellations |

### Evidence links

| Test field | Meaning |
| --- | --- |
| `executions` | Per-environment results and evidence |
| `url` | Dashboard page for the test; requires account sign-in |

### Inputs and ownership

| Field | Meaning |
| --- | --- |
| `start_url` | Submitted starting page |
| `instructions` | Submitted instructions, with surrounding whitespace trimmed |
| `files` | Supplied file source URLs |
| `project_id` | Project selected by the API key |
| `project_name` | Name of that project |

### Timing and accounting

| Field | Meaning |
| --- | --- |
| `started_at` | Execution start time; null before applicable |
| `finished_at` | Completion time after execution and cleanup; null before applicable |
| `usage` | Browser-time snapshot, when available |
| `billing` | Accounting snapshot, when available |

## Inspect each execution

| Field | Meaning |
| --- | --- |
| `environment` | Requested browser configuration |
| `actual_environment` | Observed OS and browser versions |
| `status` | Execution result or active status |
| `phase` | Current stage of work |
| `session_url` | Session evidence link; requires account sign-in |
| `error` | Null, or an object with `code` and `message` |
| `checks` | Check names, statuses, summaries, assertions, and available evidence or coverage details |
| `conditions` | Resolved browser settings and verification |

Executions also record their timestamps. Preparation can fail before a browser exists.

### Execution phases

| Phase | Stage |
| --- | --- |
| `queued` | Waiting to start |
| `planning` | Preparing the instruction plan |
| `starting` | Starting the browser |
| `executing` | Performing browser actions |
| `checking` | Evaluating requested checks |
| `cleanup` | Closing the browser and finishing cleanup |
| `finished` | Execution is finished |

Use `status` for the result and `phase` for the stage. Inspect `error`, `checks`,
and `conditions` to distinguish website failures from setup errors or insufficient evidence.

## List tests

<CodeGroup>

```bash cURL
curl --fail-with-body "https://api.browserbunny.dev/v1/tests?limit=50" \
  -H "Authorization: Bearer $BROWSERBUNNY_API_KEY"
```

```python Python
from browserbunny import BrowserBunny

with BrowserBunny() as client:
    page = client.tests.list(limit=50)
    print(page)
```

```javascript JavaScript
const response = await fetch("https://api.browserbunny.dev/v1/tests?limit=50", {
  headers: {
    Authorization: `Bearer ${process.env.BROWSERBUNNY_API_KEY}`
  }
});
const page = await response.json();
if (!response.ok) throw new Error(JSON.stringify(page));
console.log(page);
```

</CodeGroup>

- **Page size:** default 50 tests; maximum 100.
- **Next page:** pass `next_cursor` unchanged as `cursor`.

## Read logs

<CodeGroup>

```bash cURL
curl --fail-with-body "https://api.browserbunny.dev/v1/tests/TEST_ID/logs?limit=200" \
  -H "Authorization: Bearer $BROWSERBUNNY_API_KEY"
```

```python Python
from browserbunny import BrowserBunny

with BrowserBunny() as client:
    page = client.tests.logs("TEST_ID", limit=200)
    print(page)
```

```javascript JavaScript
const response = await fetch("https://api.browserbunny.dev/v1/tests/TEST_ID/logs?limit=200", {
  headers: {
    Authorization: `Bearer ${process.env.BROWSERBUNNY_API_KEY}`
  }
});
const page = await response.json();
if (!response.ok) throw new Error(JSON.stringify(page));
console.log(page);
```

</CodeGroup>

### Filter and paginate

- **Page size:** default 200 events; maximum 500.
- **Filter:** pass an execution's ID as `execution_id`.
- **Next page:** pass `next_cursor` unchanged as `cursor`.
- **Matching events:** pagination fills the page with matching events before
  returning a continuation cursor.

### Follow new events

1. Read pages until `next_cursor` is `null`.
2. Retain the returned `cursor` watermark.
3. Pass that watermark as `cursor` later to read newly appended events.

Test-level events have `execution_id: null`.

## Cancel and clean up

<CodeGroup>

```bash cURL
curl --fail-with-body -X POST "https://api.browserbunny.dev/v1/tests/TEST_ID/cancel" \
  -H "Authorization: Bearer $BROWSERBUNNY_API_KEY"
```

```python Python
from browserbunny import BrowserBunny

with BrowserBunny() as client:
    test = client.tests.cancel("TEST_ID")
    print(test)
```

```javascript JavaScript
const response = await fetch("https://api.browserbunny.dev/v1/tests/TEST_ID/cancel", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.BROWSERBUNNY_API_KEY}`
  }
});
const test = await response.json();
if (!response.ok) throw new Error(JSON.stringify(test));
console.log(test);
```

</CodeGroup>

1. Request cancellation.
2. Continue polling the test.
3. Stop once a terminal status confirms that execution and cleanup have finished.

- **Already terminal:** cancellation returns the test unchanged.
- **Local timeout or closed connection:** neither cancels the remote test.

## Read usage

Read aggregate `usage` and each execution's `usage` from the test response.

| Field or value | Meaning |
| --- | --- |
| `browser_seconds` | Browser time |
| `complete: true` | Browser time has been confirmed |
| `complete: false` | Browser time is incomplete and may change |
| `usage: null` | No snapshot is available |

Usage confirmation is independent of test status.

## Read billing

| Field | Meaning |
| --- | --- |
| `status` | Billing state |
| `amount_cents` | Amount in the reported currency's cents |
| `currency` | Billing currency |
| `credit_seconds_used` | Credit seconds consumed |
| `invoice_url` | Invoice link, when available |

Billing can settle after the test ends. Follow available minutes and billing state
in the [dashboard](https://dash.browserbunny.dev).
