Write supported conditions in ordinary `instructions`:

```python
test = client.tests.create(
    start_url="https://example.com",
    instructions='Using a 3G connection, verify the heading is "Example Domain".',
)
```

The worker resolves conditions before allocating a browser, then applies and
verifies them before the first site navigation. Conditions apply throughout an
execution. Network, locale, and timezone conditions are currently supported on
Chrome only; check `capabilities.conditions` in [environment discovery](/environments)
for deployment availability.

A `202` accepts the test for preparation. Unsupported or ambiguous conditions can
produce an execution error afterward, before allocation. Explicit environment
selection remains authoritative; instructions cannot silently switch browsers.

## Network simulation

The supported presets use BrowserBunny profile version `2026-09-25.1`:

| Preset | Download cap (kbps) | Upload cap (kbps) | Minimum response latency (ms) |
| --- | ---: | ---: | ---: |
| `3g` | 750 | 250 | 300 |
| `slow` | 400 | 150 | 400 |
| `fast` | 1600 | 750 | 150 |

Rates are decimal kilobits per second. Minimum response latency measures the
configured minimum from request sent to response headers received. You can state
exact rates, units, and this latency meaning in instructions.

These settings simulate browser traffic. They do not create a cellular connection.
Readback verifies applied configuration, not achieved throughput or RTT. Downloads
of supplied file sources happen separately from the browser's outgoing upload.

## Language and timezone

Examples:

- “Set the browser locale to es-ES and verify the page heading.”
- “Check that the website language is localized for users in Spain.”
- “Use the Europe/Madrid browser timezone and verify the page loads.”

A language-focused Spain request resolves to `es-ES` and records that assumption.
It does not change IP location, GPS, or timezone. Browser language preferences and
Intl locale are verified, with automatic translation disabled. A request to check
website language adds a separate check of sampled rendered text. Locale setup
alone does not establish that the website is localized.

Timezone emulation is verified through Intl. Website checks cover the pages and
content actually observed during the requested journey.

## Read the resolved conditions

Each execution can include:

- `conditions.requirements`: requested and resolved settings.
- `conditions.assumptions`: visible defaults used during interpretation.
- `conditions.verification`: applied settings, timestamps, evidence, and
  `verified`, `unverified`, or `error` status.
- `checks`: website assertions and other requested verification.

Unverified setup stops execution with an error. Verified conditions do not alone
make a website check pass. The accepted condition plan stays fixed within the
execution; a new submission can be interpreted differently as the service evolves.
Inspect saved resolved settings when comparing results.

## Supported scope

GPS, geographic IP routing, geofencing comparisons, staged condition changes,
offline mode, HTTP jitter, and packet loss are unavailable. Exact RTT, one-way
delay, regional pricing, and regional date or currency-format assertions are also
unsupported. The catalog marks the `lossy` preset unavailable.

Explicit desktop viewport resizing is a separate browser action. Describe the
size in instructions when needed.
