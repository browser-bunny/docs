## Request browser conditions

Write the conditions in ordinary `instructions` alongside the actions and checks:

<CodeGroup>

```bash cURL
curl --fail-with-body "https://api.browserbunny.dev/v1/tests" \
  -H "Authorization: Bearer $BROWSERBUNNY_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{
  "start_url": "https://example.com",
  "instructions": "Using a 3G connection, verify the heading is \"Example Domain\"."
}'
```

```python Python
from browserbunny import BrowserBunny

with BrowserBunny() as client:
    test = client.tests.create(
        start_url='https://example.com',
        instructions='Using a 3G connection, verify the heading is "Example Domain".',
    )
    print(test)
```

```javascript JavaScript
const response = await fetch("https://api.browserbunny.dev/v1/tests", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.BROWSERBUNNY_API_KEY}`,
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    "start_url": "https://example.com",
    "instructions": "Using a 3G connection, verify the heading is \"Example Domain\"."
  })
});
const test = await response.json();
if (!response.ok) throw new Error(JSON.stringify(test));
console.log(test);
```

</CodeGroup>

### Availability

- **Supported browser:** Chrome for network, locale, and timezone conditions.
- **Deployment support:** check `capabilities.conditions` in [environment discovery](/environments).
- **Browser selection:** instructions cannot silently replace an explicitly
  selected environment.

### Setup lifecycle

1. Resolve conditions before allocating a browser.
2. Apply and verify them before the first site navigation.
3. Keep the conditions active throughout the execution.

**Acceptance is asynchronous.** HTTP `202` accepts the test for preparation.
Unsupported or ambiguous conditions can produce an execution error before allocation.

## Network simulation

Preset values use BrowserBunny profile version `2026-09-25.1`.

| Preset | Limits |
| --- | --- |
| `3g` | Download: 750 kbps; upload: 250 kbps; minimum latency: 300 ms |
| `slow` | Download: 400 kbps; upload: 150 kbps; minimum latency: 400 ms |
| `fast` | Download: 1,600 kbps; upload: 750 kbps; minimum latency: 150 ms |

### Units and verification

- **Rates:** decimal kilobits per second.
- **Minimum latency:** configured minimum time from request sent to response
  headers received.
- **Custom values:** state exact rates, units, and that latency meaning in instructions.
- **Verification:** confirms the applied configuration, not achieved throughput or RTT.
- **File sources:** source downloads happen separately from the browser's outgoing upload.

These settings simulate browser traffic; they do not create a cellular connection.

## Locale and website language

### Example instructions

- “Set the browser locale to es-ES and verify the page heading.”
- “Check that the website language is localized for users in Spain.”

### What changes

- **Spain language requests:** resolve to `es-ES` and record the assumption.
- **Browser settings:** language preferences and Intl locale are verified;
  automatic translation is disabled.
- **Website language checks:** an explicit request adds a check of sampled rendered text.

Locale setup alone does not establish that the website is localized. It does not
change IP location, GPS, or timezone.

## Timezone

Example: “Use the Europe/Madrid browser timezone and verify the page loads.”

- Timezone emulation is verified through Intl.
- Website checks cover only the pages and content observed during the journey.

## Inspect condition evidence

Read the fields inside each execution's `conditions` object:

| Field | Meaning |
| --- | --- |
| `requirements` | Requested and resolved settings |
| `assumptions` | Defaults used during interpretation |
| `verification` | Applied settings, timestamps, and evidence |

The execution's separate `checks` field contains website assertions and other
requested verification.

### Verification statuses

| Status | Meaning |
| --- | --- |
| `verified` | Applied settings were verified |
| `unverified` | Setup could not be verified |
| `error` | Condition setup or verification encountered an error |

Unverified setup stops execution with an error. Verified conditions alone do not
make a website check pass.

### Compare repeated tests

- The accepted condition plan stays fixed within an execution.
- A new submission can be interpreted differently as the service evolves.
- Compare the saved resolved settings when reviewing results.

## Unsupported conditions

| Category | Unavailable controls or assertions |
| --- | --- |
| Location | GPS, geographic IP routing, geofencing comparisons |
| Connection behavior | Offline mode, HTTP jitter, packet loss, `lossy` preset |
| Timing | Exact RTT or one-way delay |
| Regional behavior | Regional pricing, date-format, or currency-format assertions |
| Changes during a test | Staged condition changes |

**Viewport resizing** is a separate supported browser action. Describe the
required size in your instructions.
