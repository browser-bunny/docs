## Idempotency

Every HTTP `POST /v1/runs` requires `Idempotency-Key`: 8–128 letters, numbers,
periods, underscores, colons, or hyphens. The Python SDK generates a key when you
omit it. Retain your own key when you need to retry an uncertain submission.

A new request returns `202`. Reusing the same key and request returns the existing
run's current state with `200`. Changing the URL, trimmed instructions, device
selection, project, or nonempty file list returns `409`. File order matters.
Identical replays do not dispatch another run or consume another submission attempt.

There are no automatic POST retries in the SDK. If a connection fails after
submission, retry with the same key and request. Use a new key only for a new test.
SDK platform resolution can change when the catalog changes; retain resolved
`devices` for stable retries if you need exact coverage.

## HTTP errors

| Status | Typical cause | Action |
| --- | --- | --- |
| `401` | Missing or invalid API key | Send an active project key |
| `402` | Minutes unavailable, billing not ready, or a locked target | Inspect the message and choose an available target or arrange minutes |
| `403` | Gateway authorization rejected, target disabled, or origin rejected | Check the key, account preferences, and request origin |
| `404` | Run or device test not accessible in this project | Check the IDs and project key |
| `409` | Idempotency conflict or minutes reserved by a previous run | Restore the original inputs, or wait for the previous run to settle |
| `422` | Missing header, invalid field, URL, target, or log parameter | Correct the request |
| `429` | Submission throttled or another browser run is active | Wait for `Retry-After` seconds before retrying |
| `503` | A backing service is temporarily unavailable | Retry reads; retain the idempotency key for submissions |

Application errors normally use `{"detail": "Message"}`. Request validation can
return an array in `detail`; gateway authentication errors use `message` instead.
Minute-related errors may include `code: "minutes_required"` or
`code: "minutes_pending"`. An accepted asynchronous run can later finish with an
error; that appears in the run result, not as a delayed HTTP submission response.

## Current service limits

| Setting | Current behavior |
| --- | --- |
| `start_url` | 8–2,000 characters; public HTTPS, without credentials or private addresses |
| `instructions` | 5–3,000 characters; must also meet the minimum after trimming |
| Targets per run | At most eight distinct enabled configurations |
| Concurrent runs | One active browser run across the service; additional submissions receive `429` |
| Submission attempts | Ten new attempts per account per UTC minute, shared across projects and keys |
| File source URL | At most 2,000 characters each; no separate list-count limit |
| File transfer | 10 MiB, 30 seconds, up to three redirects per file |
| Log page | 1–500 records; default 200 |
| Log query strings | `test_id` up to 128 characters; `cursor` up to 2,048 |

These are current BrowserBunny implementation limits, not AWS account quotas.
Admission attempts rejected for billing or an active browser can still count
toward the per-minute submission limit.
