## Retry a submission

Use an optional `Idempotency-Key` on `POST /v1/tests`: 8–128 letters, numbers,
periods, underscores, colons, or hyphens. Retain a stable key when you need to
retry an uncertain submission.

A new submission returns `202`. The same key and request return the existing test
with `200`. Changing the starting URL, trimmed instructions, resolved environment
selection, project, or nonempty file list with that key returns `409`. File order
matters. An identical replay does not create another execution.

Only retry an uncertain submission with its original key. Use a new key for a new test.
The release selectors `latest` and `previous` can resolve to different installed
versions over time; inspect `actual_environment` when comparing separate tests.

## HTTP errors

Application-generated errors have this structure:

```json
{
  "error": {
    "code": "not_found",
    "message": "Test not found.",
    "param": null,
    "request_id": "req_example"
  }
}
```

| Status | Typical cause | Action |
| --- | --- | --- |
| `401` | Missing or invalid API key | Use an active project key |
| `402` | Test minutes or billing readiness required | Review account minutes and the error message |
| `403` | Permission or origin rejected | Check credentials and request origin |
| `404` | Test or execution not accessible in this project | Check the IDs and project key |
| `409` | Idempotency conflict or minutes pending settlement | Restore original inputs or wait for settlement |
| `422` | Invalid fields, URL, environment, or query | Correct the indicated request |
| `429` | AWS account or service request throttling | Honor `Retry-After` when returned; back off before retrying |
| `500` | An unexpected service error occurred | Keep `request_id`; retain the key when retrying submission |
| `503` | A backing service is unavailable | Retry reads; retain the key when retrying submission |

AWS API Gateway can reject authentication or throttle a request before it reaches
the application. Those responses can use the gateway's own JSON shape, such as
`{"message": "Unauthorized"}`, and may have no application `request_id` or `req_`
identifier. Handle these errors by HTTP status when application-specific error
fields are unavailable.

Keep `request_id` for support when present. A successful asynchronous submission can later
finish with an execution error. Read `executions[].error`, conditions, and checks
for that result; it is separate from an HTTP request error.

## Current limits

| Setting | Current behavior |
| --- | --- |
| `start_url` | 8–2,000 characters; public HTTPS without credentials or private addresses |
| `instructions` | 5–3,000 characters; minimum also applies after trimming |
| Browser planning | At most eight concise browser steps per test; split longer workflows into separate tests |
| `environments` | Nonempty when supplied; distinct supported combinations after defaults |
| Queue deadline | Up to six hours to start an execution |
| Browser work | Nine minutes including browser startup, followed by cleanup and failure handling |
| File source URL | At most 2,000 characters per URL |
| File transfer | 10 MiB, 30 seconds, up to three redirects per file |
| Test page | 1–100 tests; default 50 |
| Log page | 1–500 events; default 200 |
| Cursor | At most 2,048 characters; pass the returned value unchanged |

The character limit does not guarantee that every workflow fits the planner.
Steps and generated checks share a bounded execution plan; viewport sweeps can
use several steps. Simplify or split requests that exceed that plan.

Accepted executions may queue while browser capacity is occupied. Available
minutes, credit reservations, and settlement can also affect admission. Acceptance
does not reserve an immediate browser start. Local polling timeouts can expire
while the remote test is still queued. Retain the test ID to resume polling.
